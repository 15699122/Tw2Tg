# Telegram 发送与凭据轮换

## 当前实现状态

本文描述已批准的目标行为，不代表当前产品已提供 Telegram 设置或真实发送能力。配置模型包含 `credential_rotation_resume_policy`，默认 `automatic`，但 token 验证/保存、凭据代次、待发队列授权、设置界面和生产发送接线均尚未完成。只有这些生产路径实现并完成 Windows 验收后，以下目标行为才可视为可用。实现状态以开发计划和当前平台交接记录为准。

## 三个独立设置

| 设置 | 默认 | 执行内容 |
| --- | --- | --- |
| Telegram 启用 | 关闭 | 是否允许开始新的发送请求 |
| 归档后自动发送 | 关闭 | 新归档是否生成发送意图 |
| 同一 bot 换 token 后续接策略 | 自动续接 | 是否需要额外授权旧的待发送计划 |

自动续接不会开启前两个开关。关闭归档后自动发送不撤销已入队计划；暂停全部发送应关闭 Telegram，暂停指定计划则使用计划暂停操作。

## 自动续接（默认）

应用验证候选 token 的稳定 bot ID，停止旧凭据的新领取并处理在途请求，然后激活新凭据代次。同 bot 验证成功且激活完成后，符合条件的旧计划获得续接授权。

实际请求仍要求 Telegram 已启用、目标及 endpoint 可用、文件校验成功、计划顺序依赖满足及有效领取租约。等待重试的单元保留原重试时间，不立即集中重发。旧计划保持原内容、chat、topic 和 endpoint，不使用当前默认目标重定向。

以下项目不会自动恢复：已发送、取消、永久失败、结果未知、用户暂停、缺少快照、身份无法证明关联或 endpoint 不兼容的计划。换为另一个 bot 不接管旧 bot 的队列和文件缓存。

## 确认后续接

选择 `confirm` 时，新凭据可以验证和激活，但旧队列等待明确授权。界面应展示待发送数量、等待重试数量、不可自动处理数量和原目标。用户可继续所选计划或保持暂停。授权范围持久化，重启不绕过确认。

该策略适合检查历史积压内容后再恢复。它不阻止当前设置允许的新归档产生新计划。

## 切换策略

- 自动改为确认：影响之后的凭据轮换，不撤销既有授权。需要停止既有队列时另行暂停。
- 确认改为自动：影响之后的轮换；已经等待确认的计划仍需明确授权一次。
- 仅修改策略：不发起轮换或测试发送。
- 同次保存策略和新 token：使用本次提交的策略。
- 重复保存相同 token：不产生新凭据代次或重复授权。

## 安全与不确定结果

验证失败不能破坏原有效凭据。token 不写入 SQLite、普通配置或日志，不提供回读；输入时仍会短暂存在于输入框与提交参数中，提交后应清空。

在途请求不能中途替换 token。远端可能已接受请求但本地没有确认结果时，状态为 `UNKNOWN`。两种策略都不自动重发；人工重发可能产生重复消息，必须先复核并明确接受风险。

## 消息布局

目标布局是：无媒体发送纯文字；短正文作为图片或视频的 caption；相册正文只附于选定项；长正文完整分片后独立发送媒体，不静默截断。预览不兼容时可转为 document，文件消息外观不等同于图片预览。布局设置只作用于新计划，不能改写既有快照。
